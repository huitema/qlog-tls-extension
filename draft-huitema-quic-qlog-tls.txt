                     QLOG extension for TLS events
                   draft-huitema-quic-qlog-tls-latest

Abstract

   When logging QUIC connections using QLOG, we want to capture TLS
   events that help understand the behavior of the connection, such as
   for example SNI selection or ALPN negotiation.  This draft lists the
   relevant events and proposes logging extensions.

1.  Introduction

   This document defines a qlog event schema (Section 8 of
   [I-D.ietf-quic-qlog-main-schema]) containing concrete events for the
   TLS events impacting QUIC connections [RFC9000].  QUIC use TLS 1.3
   ([RFC9846]) as defined in [RFC9001].  In addition to session
   establishment and key negotiation, QUIC connections use elements like
   Service Name Identification (SNI) or Application Layer Protocol Name
   (ALPN) that are obtained through the TLS exchange.

   The event namespace with identifier tls is defined; see Section 3.
   In this namespace multiple events derive from the qlog abstract Event
   class (Section 7 of [I-D.ietf-quic-qlog-main-schema]), each extending
   the data field and defining their name field values and semantics.
   The data types that the events use are defined in Section 6

3.  Event Schema Definition

   This document describes how the core TLS protocol and selected
   extensions can be expressed in qlog using a newly defined event
   schema.  Per the requirements in (Section 8 of
   [I-D.ietf-quic-qlog-main-schema]), this document registers the tls
   namespace.  The event schema URI is urn:ietf:params:qlog:events:tls.

3.1.  Draft Event Schema Identification

   This section is to be removed before publishing as an RFC.

   Only implementations of the final, published RFC can use the events
   belonging to the event schema with the URI
   urn:ietf:params:qlog:events:tls.  Until such an RFC exists,
   implementations MUST NOT identify themselves using this URI.

   Implementations of draft versions of the event schema MUST append the
   string "-" and the corresponding draft number to the URI.  For
   example, draft 00 of this document is identified using the URI
   urn:ietf:params:qlog:events:tls-00.

5.1.  alpn_information

   The alpn_information event supports Application-Layer Protocol
   Negotiation (ALPN) over the QUIC transport; see [RFC7301] and
   Section 8.1 of [RFC9001].  It has Core importance level.

   QUIC endpoints are configured with a list of supported ALPN
   identifiers.  During the TLS handshake, the client sends its list,
   and the server chooses one identifier from both lists and sends it
   back.  If no match is found, the connection is closed.

   ALPN identifiers are byte sequences, which are often valid UTF-8.
   The ALPNIdentifier type can hold either form: byte_value holds the
   raw bytes, and string_value holds the identifier as text.
   Implementations SHOULD log at least one form and MAY log both.

   TLSALPNInformation = {
       ? server_alpns: [* ALPNIdentifier]
       ? client_alpns: [* ALPNIdentifier]
       ? chosen_alpn: ALPNIdentifier

       * $$tls-alpninformation-extension
   }

   ALPNIdentifier = {
     ? byte_value: hexstring
     ? string_value: text
   }

                  Figure 2: TLSALPNInformation definition

   A client usually logs this event twice: first with client_alpns when
   it offers its list, then with chosen_alpn when it learns the server's
   choice.  It can instead log a single event with both fields once it
   learns the choice.

   A server logs this event once, after it chooses, with client_alpns,
   server_alpns, and chosen_alpn.
